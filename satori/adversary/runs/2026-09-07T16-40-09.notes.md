### The vulnerability
The default game (gameId 1 / `DEFAULT_STREAM_ID`, "Satori Predictions") is
special in two ways that combine badly:

1. It is UNCONDITIONALLY live and mint-eligible:
   `SatoriVoting.gameLive() = gameApproved[id] || id == DEFAULT_STREAM_ID`, and it
   carries vote weight — so correct predictions on it pay real minted SATORI.
2. Its scored value is NOT an external price. `SatoriEngine.flushDefaultStream`
   writes `_roundState[today-1].predictionCount` as the stream's value each round
   (`setValueForRound(1, count, today)`, keyed at hour `today*24`).

So the value the default game scores predictions against is the network's own
per-round on-chain prediction COUNT — a number the predictors themselves drive.
A user may submit only ONE `predictMultipleWithPayloads` per round
(`predictedStreamsCount[user][round] != 0 -> AlreadyPredicted`), so the SIZE of
that single batch is a direct lever on the count. By alternating my batch size
HIGH/LOW each round I move the count up and down on demand; the default game then
scores each of my predictions against a value I picked. The outcome reduces to
`sign(count(T+1) - count(T))`, both counts mine, so I predict the known direction
and win ~100% — on a MINT-PAYING game, with zero forecasting risk. This is
impossible on ALPHA/BETA (their value is an unforeseeable random walk) and is
exactly the "you control the value your prediction is scored against" clairvoyance
condition. Extraction (+3205 SATORI over ~10 rounds) massively beats capital share
and is pure minted emission captured by rigging a deterministic outcome.

Volume padding lands on my own UNAPPROVED filler streams held at a CONSTANT value,
so those predictions settle VOID (PredictionVoided, never scored) and never touch
the win-rate — they exist only to move the global count.

## Hypotheses tried (chronological)

1. **Pool/settle over-payment (SatoriRewards).** Read `_computeReward`,
   `_gameRoundAllocation`, `_streamPoolPostCut`, `_splitReward`,
   `scoreCorrectPrediction`. Payout is `streamPool * userWeight/totalWeight`,
   `streamPool = budget * gameVotes/totalVotes`; winners in a direction sum to
   exactly the pool, games sum to the budget, budget capped by rewardCeiling at
   mint. Commit-time weight (`_effectiveRaw*mult`, stored) == settle-time
   re-derivation (`_predRaw*_predMult`) — compression is symmetric, no drift.
   HELD: conservation-safe, no double-credit, no over-mint. No CAP path.

2. **Selective / delayed settlement of losers.** Idea: observe post before
   settling, only settle winners. BROKE as an attack: settlement scores an
   unscored slot; re-predicting a game forces its loser to score; a game has only
   2 slots and eviction is 768 ring entries (~months at daily flush). Slot reuse +
   forced scoring make loser-dropping impractical on approved streams. HELD.

3. **Timing on approved streams via advance_time.** The plain/moment-anchored
   branch anchors to the predictor's own hour and posts ~24h later; the attacker
   cannot setValue there and post is always future/random. No observability, no
   control. HELD — the random-market defense is real for approved external streams.

4. **Self-oracle padding on own unapproved games.** Control values on my own
   streams -> 100% "correct" but pays 0 (unapproved); would only game the win-rate
   metric, not extract. Set aside as not-real-theft; superseded by #5 which pays.

5. **DEFAULT game count control (THE FINDING).** See above. First attempt
   batched fillers separately from the game-1 predict -> `AlreadyPredicted` (one
   batch per round), so the count never moved (everything VOID). Fixed by putting
   game 1 + fillers in ONE batch: count alternated cleanly 6/21. Directions were
   initially inverted (0/8) — the effective window is `anchor=count(T),
   post=count(T+1)`, one round later than first modeled — flipping to DOWN-on-HIGH
   / UP-on-LOW gave 9/9 and net-positive gain. Confirmed deterministic across runs
   (independent of the honest RNG, as expected since it keys on count, not price).

## Fix direction (for the contract owner, not applied — edits confined to attack.js)
The default game should not both be force-live AND scored against a
self-referential, participant-driven value. Options: score the default game
against an EXTERNAL price feed rather than the prediction count; or make the
count-derived default stream NON-mint-eligible (informational only), so its
foreseeable/controllable outcome pays nothing — mirroring how attacker-created
self-oracle games already earn zero.
