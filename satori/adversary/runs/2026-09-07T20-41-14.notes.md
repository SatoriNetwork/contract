## Surface A — the new deployedPower / ABC default-game metric  ★ FINDING ★

### Mechanism
- Default game (id 1) is on the daily default stream (cadence 1440m = TIME_UNIT),
  so it scores via the **ABC** branch: a round-R prediction scores
  `sign(dp[R+1] - dp[R])`, where `dp[round]` is the per-round `deployedPower`
  published by `flushDefaultStream` as `deployedPower * 1e18 / totalSupply`.
- `deployedPower[round] += predictionPower` once per predict call
  (`SatoriEngine._predictMultipleWithPayloads`, line ~805).
- `predictionPower = SatoriRewards.getPredictionPower = balance + unclaimedRewards
  (+ inbound delegated)`. **Unclaimed rewards count as power but are NOT in
  `totalSupply`** (supply only grows on `claim` → `rewardMint` → `_mint`).

### Hypotheses tried
1. **Naive sign-steer (predict DOWN on even rounds, skip odd)** — score 0/12, gain 0.
   BROKE: my standing power is only ~0.51 of supply, but the honest field's
   aggregate `dp` is 6–8× supply and drifts up ~0.3–1.0/round; my ±0.5 toggle
   can't flip the marginal sign. All DOWNs lost, so no rewards, so no bootstrap.
2. **Ride the drift: predict UP every round, WITH claim** — winRate 0.5 (7/14),
   but +3283 SATORI. NOT a finding (50%, has correct calls → neither clairvoyant
   nor free-lunch). Shows the default pool is freely farmable at coin-flip odds
   for zero cost (predict burns nothing), but that alone isn't a tripped wire.
3. **Hoard test: UP every round, NEVER claim** — power ratio climbed 0.51 → 4.94
   over 16 rounds (unclaimed 0 → 6202e18). Confirms unclaimed inflates my
   deployed-power/supply ratio because the denominator excludes it.
4. **★ Compounding clairvoyance: UP every round, NEVER claim ★** — winRate **0.958
   (23/24)**, gain **+9120 SATORI**, `isFinding: true (clairvoyance)`.
   HELD. Each win credits unclaimed → my power strictly grows next round → my own
   contribution forces `dp[R+1] > dp[R]` → the UP prediction is correct → more
   unclaimed → power grows again. A **self-reinforcing loop**: I am ~half the
   supply and I *control* the value my prediction is scored against via my own
   hoarded, supply-excluded power. The lone loss is always round 0 (ratio still
   0.51 before inflation); more rounds → higher rate.
5. **Bidirectional control (phase-2 test)** — after bootstrapping power via (4),
   DOWN-on-even / skip-odd scored **14/14**. So a bootstrapped half-supply actor
   controls the sign in *either* direction at will, not just up.

### Why it's real theft (not honest lull-capture)
The default game is meant to be an unpredictable "is protocol participation
trending up?" signal. But the signal is **self-referential**: the predictor's own
deployed power is both the quantity being predicted and a quantity the predictor
controls. Refusing to claim makes it deterministically monotone. A half-supply
holder wins ~all the default pool every round at ~96–100% on a market that pays a
fixed strategy ~50%. Root causes: (a) unclaimed rewards are power but not supply,
so one actor can inflate the ratio one-directionally without bound; (b) the metric
lets a large holder dominate the round-to-round marginal.

### Suggested fix direction (not implemented — read-only mandate)
Exclude the predictor's own contribution from the value their default-game
prediction is scored against, or measure participation net of a single holder's
share, or count only *claimed*/circulating power in `deployedPower` so the ratio
can't be inflated by hoarding.

## Surface B — streak / multiplier curve
Read `_makePrediction`, `_streakWeight`, farming threshold. The streak advances
only when `_predAboveFloor` (predict-time snapshot of TOTAL power ≥
`farmingThreshold`), so a dust/empty-wallet fleet can't farm the multiplier — the
threshold gate holds. Streak-0 pays a flat ~1/7692 hook. A correct call on an
ineligible stream builds streak but pays 0 power (F16, intended). No cheap
multiplier inflation found; my Surface-A finding already saturates rewards via
power growth, not streak. Not pursued further — no obvious break.

## Surface C — delegation (double-count / replay)
`getPredictionPower` folds inbound delegated power via `_delegatePowerForRate`
(the DEFERRED rate pool), explicitly to stop a same-round receipt inflating a
delegate's slice (audit adv_6 note). Delegator returns 0 while delegated
(`di.delegate != 0`), so power isn't counted twice across delegator+delegate.
Could not exercise a two-account delegation ring in the harness (only the single
attacker signer is funded; delegating my power to an honest account just gives it
away). Reasoned-only: the deferred-pool design appears to close the obvious
double-count. NOTE: delegation is *another* vector to inflate `deployedPower` for
Surface A (inbound delegated power counts) — worth a dedicated multi-account test.
